# Аудит и подготовка StageOS 1.0.0-rc.1

## Исправленные ошибки

1. Создание постановки зависело от первой демонстрационной постановки. Теперь есть самостоятельный пустой шаблон.
2. Пустой каталог приводил к обращению к отсутствующим ID площадки и постановки. Добавлены безопасные значения и подсказка порядка настройки.
3. Карточка события пересчитывала состав и длительность по новому паспорту без изменения бронирований. Теперь показывается сохранённый план, а занятость повторно проверяется по фактическим резервированиям. Изменение паспорта отмечается отдельно.
4. Изменение утреннего выезда сдвигало обед и вечерний демонтаж. Пересчёт ограничен фиксированными границами прогона и спектакля; время погрузки корректируется перед выездом.
5. Проверялись ширина/высота декораций, но не глубина. Добавлена глубина, транспортные габариты ворот и требования подвеса с нагрузкой.
6. Время закрытия площадки не проверялось. Добавлено ограничение окончания работ.
7. Паспорт принимал неполные, ошибочно типизированные данные и повторные ссылки. Усилена проверка типов, диапазонов, квалификаций, составов, сцен и адаптаций.
8. Удаление ресурса ошибочно принимало любое совпадающее число (мощность, количество и т. п.) за его ID. Проверяются только реальные ссылки.
9. Редактирование ресурса стирало дополнительные квалификации. Теперь они сохраняются.
10. Повторное сохранение могло вернуть отменённое событие или стереть фактические работы. Перепланирование отменённых, завершённых, идущих событий и событий с введённым фактом запрещено.
11. Поиск замен мог предлагать специалиста без требуемой квалификации и дублировать одного ответственного в solver. Кандидаты берутся из допущенных исполнителей; позиции одного ответственного объединяются при поиске.
12. Недоступность здания не учитывалась для его репетиционных комнат. Добавлены проверка закрытий родительской площадки и вместимости помещения.
13. Технические участники выборочной репетиции вызывались после начала подготовки. Вызов перенесён на начало технических работ.
14. Обновление даты основного события оставляло временные закрепления этапов на старой дате. Интерфейс сдвигает их вместе с событием.
15. Некорректный импорт SQLite с валидной схемой мог переключить приложение на неисправные паспорта. Перед переключением проверяются паспорта и интервалы; отклонённый импорт не меняет активную базу.

## Инструменты создания постановки

Есть название, жанр, длительность, основная площадка; постоянные ответственные, два состава каждой роли и резерв, хор/балет/оркестр/грим/костюм, технические команды с добавлением цехов; комплекты и отдельные экземпляры оборудования, декорации, реквизит, костюмы, транспорт; технические требования; параллельные этапы подготовки, сцены репетиции, адаптации площадок. Добавлены отдельные текстовые паспорта звука, света, видео, сценических работ, костюмов, реквизита, логистики и особых условий. Подготовка рассчитывается по длительности критического пути, а не хранится как независимая ручная оценка.

Сотрудник создаётся в каталоге с цехом и квалификацией; в постановке выбирается существующий ID. Количество N имущества создаёт N физических ресурсов. Для декораций доступны габариты, масса, транспортные размеры, необходимость подвеса, длительность установки и требуемая команда. Последние два свойства пока являются паспортными данными: длительности и люди рабочего плана задаются в производственных этапах и составе.

## Границы готовности

Это не доказательство отсутствия всех ошибок. Проверки охватывают реализованные локальные сценарии, в том числе пустую базу. Запуск окна на Windows 10/11 остаётся отдельным приёмочным условием. Автоматизация Windows включена в GitHub Actions; её фактический результат нужно читать по конкретному запуску.

- Два состава A/B фиксированы; произвольное число составов пока не поддерживается.
- Технические текстовые паспорта, схемы сигналов и меры безопасности — описательные поля. Solver не моделирует электрическую схему, динамику конструкций или полную ведомость работ по каждому прибору.
- Часы перерывов пока входят в непрерывное консервативное резервирование людей.
- Оборудование выбирается по конкретным единицам; автоматического баланса складских остатков по обезличенному типу нет.
- Адаптация меняет требования, оркестр и классические декорации; общие поштучные items остаются необходимыми во всех адаптациях.
- Редактирование паспорта требует отдельного пересчёта сохранённых событий. Отменённые события не восстанавливаются редактированием.
- Локальные модели и PostgreSQL не проходили проверку реальной интеграции. Многопользовательские права, серверный доступ и синхронизация не входят в эту локальную сборку.
- Portable использует Win32 + pywebview/WebView2. Tauri/NSIS не объявлены собранными.

Фактические результаты: TEST_RESULTS.md и BUILD_RESULTS.md.
